## Scope
The main purpose of this database is to organize and, consequently, be able to analyze Walmart's weekly store sales (https://www.kaggle.com/datasets/yasserh/walmart-dataset) together with the economic and environmental conditions associated with each week.
The design of this database allows to conduct store-level and time-based analysis of sales performance. Therefore, users can compare stores, identify periods of particularly high or low sales, and examine how sales change across weeks and holiday periods.
The database includes three types of information:
- Walmart stores;
- the weeks of reference and whether the corresponding week was classified as a holiday week, together with the temperature, fuel price, Consumer Price Index (CPI), and unemployment rate recorded;
- the weekly sales generated by each store.
The database is intentionally limited to the information available in the original dataset; therefore it focuses specifically on aggregated weekly store performance rather than operational or customer-level retail management.

## Functional Requirements
A user should be able to retrieve and compare weekly sales across Walmart stores and time periods.
In particular, the database should allow users to identify stores with the highest or lowest total and average sales, examine sales during individual weeks, and compare sales between holiday and non-holiday periods. Users should also be able to analyze weekly sales together with the economic and environmental variables associated with each week, such as fuel price, CPI, unemployment, and temperature.
Therefore, the database should support basic data-management operations.
Authorized users should also be able to add new stores or weekly observations, update existing records, and remove records that were entered incorrectly.
Predefined views should simplify daily performed analyses, while indexes should improve the performance of common searches.
The database does not support real-time retail operations or transactional management. Users should not be able to use it to manage individual purchases, customers, products, inventory, employees, or payments, as these types of information are not represented in the dataset.
Its purpose is analytical, not operational: it provides a structured way to investigate historical weekly sales patterns rather than to manage Walmart stores in real time.


## Representation
### Entities
The database represents three main entities: stores, weeks, and weekly sales. These entities reflect the structure of the original dataset.
- Stores
The stores table represents the Walmart stores included in the dataset.
Each store is identified by a unique store_id, of type INTEGER, which serves as the table's primary key.
The PRIMARY KEY constraint ensures that each store is uniquely identified and prevents duplicate store records.
The store_id is represented as an INTEGER because the original dataset identifies stores using numerical identifiers without decimal values. The table contains only the store identifier because the dataset does not provide additional information about individual stores, such as their location, size, or number of employees.
- Weeks
The weeks table represents the weeks for which sales observations are available. Each week is identified by a unique week_id, of type INTEGER, which serves as the primary key.
The table also stores the corresponding date, temperature, fuel_price, CPI, and unemployment values.
The date is stored as TEXT because SQLite does not provide a dedicated date data type. The dates follow a consistent format, allowing them to be ordered and compared correctly. A UNIQUE constraint is applied to date so that the same week cannot be represented more than once.
The environmental and economic variables (temperature, fuel_price, CPI, and unemployment) are stored as REAL values because they can contain decimals. These attributes are also defined as NOT NULL because every weekly observation in the source dataset contains a value for them, and the constraint ensures that future records cannot be inserted without these values.
The holiday_flag is stored in this table, since it describes a property of the week itself (whether it corresponds to a holiday week or not): for a given week, the value is identical across all stores. It is represented as an INTEGER with a CHECK constraint restricting its value to 0 or 1.
- Weekly Sales
The weekly_sales table represents the sales generated by each Walmart store in each week. Each record contains a unique sale_id, the corresponding store_id, the corresponding week_id, and the weekly_sales amount.
The sale_id is an INTEGER primary key used to uniquely identify each record.
store_id and week_id are also stored as INTEGER values because they reference the primary keys of the stores and weeks tables. Both store_id and week_id are defined as NOT NULL and as foreign keys. This ensures that every weekly sales observation is associated with an existing store and an existing week.
weekly_sales is represented as a REAL because sales values can contain decimals. It is defined as NOT NULL because every observation in the original dataset contains a sales value.
Finally, a UNIQUE constraint is applied to the combination of store_id and week_id. This constraint does not require store_id or week_id to be unique on their own — indeed, the same store_id appears in multiple rows (one per week in which that store has a recorded sale), and the same week_id appears in multiple rows (one per store that had a sale that week). What the constraint prevents is the same pair (store_id, week_id) from appearing twice, ensuring a store has at most one sales observation per week and preventing accidental duplicate records.

## Optimizations
To improve query performance and make the database easier to use, indexes and views were created.
An index was created on weekly_sales.store_id to improve queries that filter or group records by store, such as computing total or average sales per store. Since the database contains weekly observations for multiple stores, store-level queries are frequent and can benefit from indexing.
An index was also created on weekly_sales.week_id to improve the performance of joins between weekly_sales and weeks, which are needed whenever sales are analyzed together with the economic and environmental variables associated with a given week.
An index was created on weeks.holiday_flag to improve queries that compare sales between holiday and non-holiday periods, since this type of comparison is one of the main analyses supported by the database.
No additional index was created on weeks.date or on the combination of weekly_sales.store_id and weekly_sales.week_id, since SQLite automatically creates an index to enforce the UNIQUE constraints already defined on these columns.
Views were created to simplify commonly used analyses and provide reusable query results. Instead of repeatedly writing complex queries, a view can encapsulate the required joins, filtering, or aggregation and make the database easier to query and analyze.
These optimizations were chosen because the database is primarily intended for store-level and time-based analysis. They improve the efficiency and readability of frequently performed queries while keeping the database structure relatively simple.

## Limitations
The main limitation of the database is that it is based on weekly store-level data.
Therefore, it cannot represent changes that occur within a week, such as daily fluctuations in sales, temperature, or other economic conditions. Events that happen during a specific day may therefore be hidden by the weekly aggregation.
The database also contains a limited set of variables, other factors that may influence sales, such as promotions, product availability, local events, store characteristics, or competitors' activity, are not represented.
Another limitation is that the economic and environmental variables are associated with the week rather than with individual transactions or products. As a result, the database cannot provide detailed analysis at the product or transaction level.
Additionally, the database itself does not enforce user authorization: SQLite does not provide a built-in system of user roles or permissions comparable to other DBMSs. Restricting who is allowed to add, update, or delete records is therefore a responsibility that must be handled at the application level, outside of the database schema.
Finally, the database is designed around the structure and variables available in the original dataset. It is therefore suitable for analyzing the relationships between store sales and the available external conditions, but it cannot fully represent the overall set of factors that may explain differences in retail performance.
